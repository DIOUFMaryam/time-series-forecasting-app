# Time Series Forecasting App

A web app (built with [Shiny for Python](https://shiny.posit.co/py/)) for exploring, diagnosing, and forecasting business KPI time series. Built during an internship to help non-technical analysts get a trustworthy forecast without hand-picking a model themselves.

![App overview](images/app.png)

## What it does

Given an Excel file of time-indexed KPIs, the app:

1. **Diagnoses the series** — stationarity (DF-GLS, a variant of the ADF test, plus Phillips-Perron and KPSS), trend strength, seasonality, data volume, and missing values.
2. **Recommends a model** — a rule-based heuristic (see below) picks between SARIMA, Prophet, and LSTM based on that diagnosis, instead of leaving the user to guess.
3. **Trains and validates** — fits the chosen model, plots actual vs. predicted, and reports error metrics (MAE, RMSE, MAPE) plus residual diagnostics (Ljung-Box for autocorrelation, Breusch-Pagan for heteroscedasticity).
4. **Forecasts and exports** — generates a future horizon and lets the user download it as Excel.

## Why the model-selection logic is the interesting part

Most "forecast my time series" projects just fit one model, or fit three and pick the best score in hindsight. This app instead encodes a small decision tree *before* training:

- Small data + low missingness + no strong trend/seasonality → **SARIMA** (classical models need less data and are more interpretable when the series is well-behaved).
- Strong trend or seasonality with non-stationarity → **Prophet** (handles trend/seasonality changepoints natively without manual differencing).
- Larger, well-populated series without a Prophet-favoring signal → **LSTM** (worth the extra data and training cost when there's enough of it to learn from).

This lives in `select_model()` in `app/server.py`.

## Data

The original app ran on confidential KPI data from a mobile operator, which is not included here. The repository instead ships a **synthetic dataset** with the same structure: ten years of monthly data (2015-2024) for eight fictional telecom KPIs, generated by `scripts/generate_synthetic_kpis.py` with a fixed seed.

Each KPI is designed to exercise a different part of the diagnosis and models:

| KPI | Behaviour |
|---|---|
| Active subscribers (k) | S-shaped growth that saturates, mild seasonality |
| Data traffic (TB) | Exponential growth, multiplicative seasonality |
| Voice traffic (M minutes) | Grows until 2018, then declines as usage moves to data |
| ARPU (EUR) | Slow decline with noise |
| Mobile money transactions (k) | Launched mid-2017 (missing values before), level shift in 2020 |
| Churn rate | Stationary, mean-reverting, January bump |
| Customer care calls (k) | Tracked from 2016, seasonal, outage spikes |
| Revenue (M EUR) | Built from the other KPIs: trend + seasonality |

To use your own data, drop an `.xlsx` file in `files/` with dates in the first column and one numeric column per KPI (monthly frequency). KPI descriptions and saved model parameters are optional: KPIs missing from `kpi.ods` simply use default parameters.

## Getting started

Tested on **Windows with Anaconda and Python 3.10**. The pinned versions in `requirements.txt` (pandas 2.0.3, numpy 1.24.3, TensorFlow 2.14.1, Prophet 1.1.5...) need Python 3.9-3.11; a newer Python will fail at install time. Use a dedicated environment.

1. Open **Anaconda Prompt** (a terminal, not the Spyder/IPython console) and create the environment:
   ```bash
   conda create -n tsf python=3.10
   conda activate tsf
   ```
   The prompt should now start with `(tsf)`. If you already have a `tsf` environment from an older version of the app, pick another name (e.g. `tsf-shiny1`) so both can coexist; `conda env list` shows the names already in use.
2. Install the dependencies:
   ```bash
   cd path\to\TSF\app
   pip install -r requirements.txt
   ```
3. The demo data (`files/telecom_kpis_synthetic.xlsx` and `kpi.ods`) is included. To rebuild it, run `python ..\scripts\generate_synthetic_kpis.py` (this also resets any model parameters saved in `kpi.ods`).
4. Start the app from the `app` folder:
   ```bash
   python myapp.py
   ```
   `shiny run myapp.py` also works, and `shiny run --reload myapp.py` restarts the app whenever a file is saved, which is handy while editing.
5. Open `http://127.0.0.1:8000`. Pick an Excel file from `files/`, pick a column, and use the sidebar tabs (Time Series Plot → Data → Model → Forecast → Documentation).

The first start takes a little while (Prophet is a heavy import), and TensorFlow only loads the first time an LSTM model is requested. The LSTM model trains from scratch on each request, so that tab is slow by design. To stop the app, press `Ctrl+C` in the terminal. Next time, only `conda activate tsf` and step 4 are needed.

## Deployment

The live demo runs on [Posit Connect Cloud](https://connect.posit.cloud), published from this GitHub repository: primary file `app/myapp.py`, Python 3.10, and the environment variable `TSF_READ_ONLY=1`. Read-only mode hides the "Save" buttons so visitors can't overwrite the saved model parameters or the documentation that every visitor sees.

### Running from Spyder

1. With the environment active in Anaconda Prompt, run `pip install spyder-kernels`. If Spyder later reports a version mismatch, it names the version to install.
2. In Spyder, go to **Tools → Preferences → Python interpreter**, choose "Use the following Python interpreter" and select the environment's `python.exe` (`where python` in Anaconda Prompt shows its path).
3. Restart the console, open `app/myapp.py` and run it. Spyder runs a file from its own folder by default, so the relative paths work. `nest_asyncio` (applied in `myapp.py`) is what lets the app run inside Spyder's console.
4. To stop the app, interrupt or restart the console. If a second run reports that the address is already in use, restart the console first.

## Troubleshooting

Problems hit while getting this app running again on a fresh Windows machine, and what fixed them:

| Symptom | Cause | Fix |
|---|---|---|
| `Failed to build 'pandas'` / `No module named 'pkg_resources'` | Python too new for the pinned versions, pip tries to build pandas from source | Use a Python 3.10 environment (step 1) |
| `ResolutionImpossible`: `tensorflow-intel 2.13.1 depends on typing-extensions<4.6.0` | Shiny 1.x (via `htmltools`) needs `typing_extensions>=4.10`, which TensorFlow 2.13 refuses | `requirements.txt` now pins `tensorflow==2.14.1`, the first version without that cap |
| `ImportError: cannot import name 'TypeIs' from 'typing_extensions'` | `htmltools` needs `typing_extensions>=4.10` | Already in `requirements.txt`; reinstall with the provided file |
| `DLL load failed ... Une stratégie de contrôle d'application a bloqué ce fichier` | Windows Smart App Control blocked a TensorFlow DLL | The app still starts (TensorFlow loads lazily) and LSTM shows as "unavailable"; SARIMA and Prophet are unaffected. Smart App Control has no per-app exception. Workarounds: run the app under WSL (Linux) or on a Linux host, or turn Smart App Control off (on many Windows versions it cannot be turned back on without resetting Windows). On the test machine the block has come and gone between installs |
| `invalid command name ".!canvas"` in the Model tab | matplotlib's default Tk window backend does not work inside the web server's threads | Fixed in code: matplotlib is forced to the `Agg` backend |
| `'Prophet' object has no attribute 'stan_backend'` | Prophet 1.1.5's bundled Stan folder has no `makefile`, and `cmdstanpy` 1.3 rejects it. The message hides the real error | `pip install cmdstanpy==1.1.0` (already in `requirements.txt`). To see the real error: `python -c "from prophet.models import CmdStanPyBackend; CmdStanPyBackend()"` |

## Known issues / honest limitations

- **LSTM on Windows 11 with Smart App Control**: TensorFlow can be blocked (see Troubleshooting). The rest of the app works without it.
- **Pinned, ageing stack**: the pins keep the app on Python 3.9-3.11, numpy 1.24 and Prophet 1.1.5. The Shiny upgrade is done; the remaining plan is pandas/statsmodels, then Prophet and TensorFlow (TensorFlow 2.16+ switches to Keras 3, so the LSTM code will need retesting).
- **LSTM is trained from scratch per request**: there's no caching, so switching KPIs retrains the model live, and the rest of that visitor's session waits while it trains (the default settings keep this to seconds; larger custom settings make it longer). Fine for a demo/internal tool, not for production latency.
- **Single-series models only**: each KPI is forecast independently; no cross-series (multivariate) modeling.
- **Monthly data only**: horizons, seasonal periods and forecast dates assume one observation per month.
- **The LSTM is never the recommended model on monthly data**: the recommendation needs 1,000+ observations for LSTM, i.e. 80+ years of monthly history. It can still be selected manually.
- **No automated tests**: diagnostics and metrics are validated visually in the app, not with a test suite.

## Fixed since the internship version

A few correctness issues found on review, since fixed in this repo:
- **LSTM data leakage**: the scaler used to be fit on the *entire* series (train + test) before splitting, leaking test-set scale into training. It's now fit on the training split only, in both the single-KPI path and the multi-KPI batch forecast.
- **MAPE division-by-zero**: KPI series with zero-valued periods could produce `inf`/`nan` MAPE. Zero-actual points are now excluded from the MAPE calculation instead of silently corrupting it.
- **Prophet cross-validation windows**: were hardcoded in days (`366/180/180`) regardless of how much history a given KPI actually had. Windows are now scaled to each series' own date range.

Fixed while moving to the public synthetic dataset:
- **SARIMA order selection (very slow fits)**: `p` and `q` counted *every* significant lag of the undifferenced series (the code comment said "take the first significant lag"), so a trend pushed `q` to 8-10, and `P`/`Q` were read from non-seasonal lags of the residuals. Orders are now read on the differenced series, where the ACF/PACF cuts off (capped at 3), with `P`/`Q` set from lag 12. Typical result: SARIMA(1,1,1)(1,0,1,12) instead of SARIMA(1,1,9)(4,0,1,12), which fits in seconds instead of minutes and overfits far less.
- **SARIMA order selection crash** ("Residuals are all zero and so automatic bandwidth selection cannot be used"): to pick `d`, the series was differenced until the stationarity tests agreed, with no limit. Once over-differenced, KPSS's automatic lag selection estimates a negative long-run variance and `arch` raises an error. KPSS now uses a fixed number of lags (whose estimate can't be negative), `d` is capped at 2, and a test that can't run no longer crashes the app. The Data tab's stationarity verdict uses the same function.
- **Data summary crash**: the median's date was found by looking for a value exactly equal to the median, which usually doesn't exist when a series has an even number of points (the median is then the average of the two middle values). The summary now shows the date of the closest observation.
- **KPIs missing from `kpi.ods`**: a KPI without a row in the saved-parameter sheets raised a `KeyError` as soon as "Use saved parameters" was ticked. Missing or incomplete rows now fall back to the default parameters, and a missing `kpi.ods` is handled the same way.
- **Forecast tab KPI list**: was read from `kpi.ods` instead of the loaded file, so it could list KPIs the file doesn't have. It now lists the file's columns.

Prepared for deployment:
- **Faster default LSTM**: batch size 16 instead of 1 and no per-epoch logging. With batch size 1, the training behind the Forecast tab's model comparison took minutes on the server and froze the tab's download and forecast buttons until it finished.
- **Paths** are built from the project folder instead of the folder the app is started from (`../files` only worked when started from `app/`).
- **Read-only mode** (`TSF_READ_ONLY=1`) for the public demo.
- **`nest_asyncio`** (needed for Spyder) is only applied when `myapp.py` is run directly, leaving a hosting server's event loop alone.

Fixed while getting the app running again:
- **TensorFlow is imported lazily**: it used to be imported at startup, so a TensorFlow import failure crashed the whole app. It now loads only when an LSTM model is built; if it can't load, the LSTM tab and the LSTM column in the comparison show "unavailable" and the other models keep working.
- **matplotlib backend** forced to `Agg` (see Troubleshooting).
- **Pinned `cmdstanpy==1.1.0`** to match Prophet 1.1.5 (see Troubleshooting).

Migrated to Shiny for Python 1.x (previously pinned to 0.6.1.1):
- **Layout and API**: `ui.panel_sidebar`/`ui.panel_main` → `ui.sidebar` inside `ui.layout_sidebar`; `ui.nav` → `ui.nav_panel`; `@reactive.Calc`/`@reactive.Effect` → `@reactive.calc`/`@reactive.effect`; `@session.download` → `@render.download`; `@output` decorators removed.
- **TensorFlow 2.13.1 → 2.14.1** to resolve the `typing_extensions` conflict with Shiny 1.x. 2.14 keeps the same Keras API, so the LSTM code is unchanged.
- **Excel download** now writes with `openpyxl` (it used `xlsxwriter`, which was never in `requirements.txt`, so the button failed).
- **Parameter checkboxes**: ticking "Use saved parameters" while "Choose model parameters" was ticked immediately unticked the box just clicked; the two now switch cleanly.
- **Batch forecast with LSTM** loaded the saved parameters of the KPI selected in the sidebar instead of each KPI being forecast.
- **Outputs returning the wrong type** (DataFrames from text/UI outputs, which Shiny 1.x rejects) and a browser tab titled "True".
- **Prophet with short history**: the Performance tab now shows a message instead of crashing when cross-validation has too little data.

Library-compatibility fixes, so the code keeps working when the pins move:
- **`sarima_model.py`**: removed `use_line_collection=True` from `plt.stem` (removed in matplotlib 3.8) and the no-op `plt.show()` calls.
- **`prophet_model.py`**: the forecast frequency `'m'` is now `pd.offsets.MonthEnd()`, since month-end text aliases changed in pandas 2.2. Forecast dates are unchanged.
